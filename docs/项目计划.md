## 2. 总体架构

实际形态（与最初规划的差异：**不用消息队列**——判题任务由 API 进程内嵌的 gRPC 网关直推给主动外连的节点，Redis 只作预留；新增 **assistant-node** 与判题节点同构）：

```
web/ (Vue3 SPA) ──HTTP/SSE──► api/ (FastAPI :8000)
                                 ├─ 判题网关 gRPC :50051 ◄──bidi── judge/judge_node (nsjail 沙箱容器)
                                 ├─ 助手网关 gRPC :50060 ◄──bidi── agent/assistant_node (Anthropic SDK)
                                 ├─ PostgreSQL 16（20 张表，Alembic 迁移）
                                 └─ MinIO（题目测试数据 / 头像，可切本地盘）
```

**核心设计原则（三条全部兑现）**
1. **Web 服务与判题机彻底分离**：判题机不暴露公网、无入站端口，只出不进；
2. **节点无状态、可水平扩展**：多节点各自外连注册，网关按 capacity 轮询调度；
3. **所有用户代码必须进沙箱执行**：nsjail 全 namespace 隔离 + nobody 运行，`run_on_sample` 与自测同走此路。

详细分层与逐模块操作清单见 [系统架构设计.md](系统架构设计.md)。

## 5. 关键风险与对策（实测校准后）

| 风险 | 等级 | 现状 |
|------|------|------|
| **沙箱逃逸**（公网最大风险） | ★★★ | nsjail 全 namespace + nobody + rlimit 已落地并 12 场景实测；**防逃逸专项审计仍待做（阶段 4）** |
| 测试数据泄露 | ★★★ | 已三层收口：数据只经网关 token 流式下发给节点；API 永不返回 `.in/.out`（助手学生面同禁）；助手节点零存储访问。审校面截断预览是唯一受控例外（can_manage 实时校验 + 声明面隔离） |
| AI 被用于比赛作弊 | ★★★ | **红线已实现并抽测通过**：赛中参赛者 `/assistant/chat` 一律 403、前端入口置灰、赛后自动恢复；拒绝 Hints-Only 降级 |
| 比赛高峰判题积压 | ★★ | 节点 capacity 信号量 + waiting 队列 + 结果回传即补位；**压测未做** |
| Anthropic token 成本 | ★★ | 日配额 100 轮 + `run_on_sample` 20 次 + 用量看板可观测；`assistant_title_summary` 有开关 |
| Python 调度性能 | ★ | 网关只做 IO 与编排，重活在沙箱/子进程（`to_thread` 不卡事件循环） |
