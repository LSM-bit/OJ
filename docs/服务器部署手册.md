# OJ 服务器部署手册（Linux + Docker）

> 目标环境：Linux 服务器（Ubuntu 22.04/24.04 或 Debian 12 均可），Docker Engine + compose 插件。
> 部署形态：**全容器化**——api/web/postgres/redis/minio/judge-node/assistant-node 七个容器，
> nginx（web 容器内）为唯一公网入口 :80，域名直接解析到服务器 IP。
> 站点对外挂在 **`/oj/` 子路径**下（`http://域名/oj/`），根路径 302 跳转到 `/oj/`（兼容旧链接）。

## 1. 部署架构

```
公网 → 域名(:80) → nginx (web 容器, 唯一入口)
                      ├─ /oj/          前端 dist 静态托管（SPA try_files 回退）
                      │                （dist 落在容器 /usr/share/nginx/html/oj/，与 URL 前缀一致）
                      ├─ /oj/api/  ─── 反代剥离前缀 → api 容器 :8000
                      └─ /           ── 302 → /oj/（旧链接/书签兼容）
                                                    ├─ postgres / redis / minio（容器内服务名直连）
                                                    ├─ :50051 ← judge-node（nsjail 判题，privileged）
                                                    └─ :50060 ← assistant-node（AI 助手，含 LLM key）
```

要点：infra 端口（5432/6379/9000/9001）仅绑定 127.0.0.1 供服务器本机调试，**不对外**；
api 容器不发布任何端口；对外只有 80。所有跨容器连接走 compose 网络服务名，不依赖 host.docker.internal。
容器命名规则（专属服务 `deploy-oj-*`、基础设施保留自动名）见 §8.5。

## 2. 服务器环境准备（从零开始）

### 2.1 系统与基础工具

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y curl git wget ca-certificates gnupg
sudo timedatectl set-ntp true        # 时间同步（打卡按自然日、JWT 有有效期）
```

### 2.2 Docker Engine + compose 插件（已安装则跳过）

```bash
# Docker 官方安装脚本（Ubuntu/Debian）
curl -fsSL https://get.docker.com | sudo sh
sudo systemctl enable --now docker

# 当前用户加入 docker 组（免 sudo 跑 docker 命令）
sudo usermod -aG docker $USER && newgrp docker
```

安装后验证：

```bash
docker --version          # ≥ 24
docker compose version    # compose 插件（v2，不是 docker-compose 老命令）
docker run --rm hello-world
```

> **privileged 能力检查**：judge-node 需要 `--privileged`（nsjail 沙箱要 user/net namespace）。
> 若服务器是 OpenVZ 等虚拟化或容器服务商禁用 privileged，判题节点无法启动，需换 KVM 类服务器。

### 2.3 Python 3 环境（服务器本机，运维/调试用）

> 核心服务已全部容器化，**不依赖本机 Python**。但建议装一份，用于：连本机 postgres
> 调试、跑数据迁移脚本、生成密钥等运维操作。

```bash
sudo apt install -y python3 python3-pip python3-venv
python3 --version    # ≥ 3.10 即可（容器内自带 3.12，本机版本无关紧要）
```

### 2.4 镜像源（国内服务器）

直连 docker.io 常被墙，建议配镜像加速器（`/etc/docker/daemon.json` 写 `registry-mirrors`，
然后 `sudo systemctl restart docker`）——postgres / redis / python / node 等基础镜像都走它。

**例外：MinIO**。MinIO 已于 2026-09 删除 Docker Hub 上的 `minio/minio` 镜像，官方名必定
报 `denied`，**配加速器也没用**（加速器只是转发 docker.io，上游仓库已 404）。compose 里已
改用官方上游 `quay.io/minio/minio:latest`（本机与服务器实测均可直连）。若你的网络拉不动，
把 compose 里 minio 的 `image` 换成代理缓存：`docker.1ms.run/minio/minio:latest` 或
`docker.m.daocloud.io/minio/minio:latest`。

```bash
git clone https://github.com/LSM-bit/OJ.git && cd OJ
```

## 4. 配置密钥（deploy/ 下，全部已 gitignore 绝不入库）

### 4.1 api.env（postgres / minio / api 三服务共用）

```bash
cd deploy
cp api.env.example api.env

# 生成随机值（把占位符替换成下面的输出）
openssl rand -hex 32    # JWT_SECRET
openssl rand -hex 24    # POSTGRES_PASSWORD / MINIO_ROOT_PASSWORD / 两个节点令牌（各生成一个）

vi api.env
```

编辑 api.env 时**核对三处一致性**（填错会连不上/认证失败）：

| 一致性项 | 说明 |
|---|---|
| `DATABASE_URL` 里的密码 == `POSTGRES_PASSWORD` | postgres 初始化凭据与 api 连接串 |
| `MINIO_ROOT_PASSWORD` == `MINIO_SECRET_KEY` | minio 初始化凭据与 api 客户端凭据 |
| `JUDGE_GATEWAY_TOKENS[0]` == judge-node.env 的 `SERVER_TOKEN` | 判题节点认证 |
| `ASSISTANT_NODE_TOKENS[0]` == .env 的 `SERVER_TOKEN` | 助手节点认证 |

注意：`JUDGE_GATEWAY_TOKENS` / `ASSISTANT_NODE_TOKENS` 是 **JSON 数组语法**，引号方括号原样保留。

### 4.2 judge-node.env

```bash
echo 'SERVER_TOKEN=<刚生成的判题令牌>' > judge-node.env
```

### 4.3 .env（AI 助手节点）

```bash
cat > .env <<'EOF'
ANTHROPIC_API_KEY=<你的 LLM API Key>
ANTHROPIC_BASE_URL=<API 中转端点，无中转则删掉此行>
SERVER_TOKEN=<刚生成的助手令牌>
EOF
```

### 4.4 权限与验收

```bash
chmod 600 api.env judge-node.env .env    # 密钥文件收紧权限
# 自检：三个文件应全部被 git 忽略（无输出=已忽略）
git check-ignore api.env judge-node.env .env
```

## 5. 启动

```bash
# 5.1 判题基础镜像（工具链 / JDK21 / nsjail / gRPC）：回到仓库根目录构建，只需一次，约 5~15 分钟。
#     判题节点拆两层，本层极少变；日常重建只走上层 judge-node（几秒），不再重装工具链。
cd .. && docker build -f deploy/judge-base.Dockerfile -t oj-judge-base:24.04 . && cd deploy

# 5.2 全量构建启动（首次约 5~15 分钟：api 装依赖 + web npm ci）
docker compose -f docker-compose.yml -f compose.prod.yml up -d --build

docker compose -f docker-compose.yml -f compose.prod.yml ps
# 期望：7 个服务全部 Up（healthy）
```

> **升级已有部署（2026-09 容器改名）**：专属服务容器名由自动名 `deploy-<服务>-1` 改为显式名
> `deploy-oj-<服务名>`（规则见 §8.5）。服务器上若已跑着旧容器，**必须先清掉旧容器再 up**，
> 否则旧 web 容器仍占着 80 端口，新容器起不来：
>
> ```bash
> docker rm -f deploy-web-1 deploy-api-1 deploy-judge-node-1 deploy-assistant-node-1
> docker compose -f docker-compose.yml -f compose.prod.yml up -d --build
> ```
>
> 全新服务器首次部署无需处理（无旧容器，删不存在的容器报错但无害）；走 `bash deploy/update.sh`
> 更新的话，该脚本已内置这一步。

首次启动自动完成：alembic 迁移建表 → 创建初始管理员（api.env 的 ADMIN_USERNAME/PASSWORD）→ 起 uvicorn。
`healthy` 状态隐含迁移已成功（迁移失败则 uvicorn 不启动、健康检查不通过）。

## 6. 首次启动验证

```bash
# 1. 迁移与管理员日志
docker compose -f docker-compose.yml -f compose.prod.yml logs api | grep -E "Running upgrade|管理员"

# 2. API 健康 + 判题节点在线（注意子路径前缀 /oj）
curl -s http://127.0.0.1:80/oj/api/health         # {"status":"ok"}
curl -s http://127.0.0.1:80/oj/api/health/judges  # {"online_nodes":1,...}（节点重连约 10s）

# 3. 静态托管与 SPA 回退（都返回 HTML）
curl -s http://127.0.0.1/oj/ | head -3
curl -s http://127.0.0.1/oj/problems | head -3

# 4. 根路径兼容跳转（期望 302，Location 指向 /oj/...）
curl -si http://127.0.0.1/ | head -1
curl -si http://127.0.0.1/problems | grep -i '^Location'
```

## 7. 域名与验收

1. DNS 控制台加 **A 记录**：域名 → 服务器公网 IP（如 `oj.example.com`）；
2. 服务器安全组/防火墙放行 **80/tcp**（生产建议只放 80；本机调试端口全是 127.0.0.1 不需放行）；
3. 浏览器验收清单：

| 项 | 操作 |
|---|---|
| 登录 | 用 ADMIN_USERNAME/ADMIN_PASSWORD 登录成功，**立即到个人页改密** |
| 判题 | 上传/提交一道题，正常出 AC/WA 结果 |
| AI 助手 | 非比赛时提问，回复**逐字流式**输出（缓冲卡住=SSE 配置问题） |
| 头像 | 上传头像后刷新可见 |
| 文件上传 | 后台传一道 50MB 级测试数据压缩包，成功（上限 64MB） |

4. 全部通过后，把 nginx 配置的 `server_name _` 改成你的域名（deploy/nginx/default.conf），`up -d --build` 重建 web 即可。

## 8. 日常运维

### 8.1 更新上线

```bash
cd OJ
bash deploy/update.sh          # 拉代码 + 重建启动（基础镜像缺失时自动构建）
bash deploy/update.sh --base   # 改了 judge-base.Dockerfile 或升级依赖时才用（重建基础镜像）

# 脚本等价于：
#   git pull --ff-only
#   docker build -f deploy/judge-base.Dockerfile -t oj-judge-base:24.04 .   # 仅 --base 或镜像缺失时
#   docker rm -f deploy-web-1 deploy-api-1 deploy-judge-node-1 deploy-assistant-node-1   # 一次性：清旧名容器（§8.5）
#   cd deploy && docker compose -f docker-compose.yml -f compose.prod.yml up -d --build
# api 容器每次启动都会跑 alembic upgrade head（幂等）+ create_admin（幂等），
# 所以「迁移与重启同批」由容器天然保证
```

### 8.2 备份（每天 cron 建议）

```bash
# 数据库
docker compose -f docker-compose.yml -f compose.prod.yml exec -T postgres \
  pg_dump -U oj oj > oj_backup_$(date +%F).sql
# 对象存储：rsync 卷目录或 MinIO mc mirror 到异地
docker run --rm -v ojminiodata:/data -v $PWD:/backup alpine \
  tar czf /backup/minio_$(date +%F).tgz -C /data .
```

### 8.3 日志与状态

```bash
docker compose -f docker-compose.yml -f compose.prod.yml ps
docker compose -f docker-compose.yml -f compose.prod.yml logs -f api judge-node   # 按服务名（推荐）
docker logs -f deploy-oj-api                                                     # 按容器名（§8.5 的新名字）
```

日常排障也可直接看管理后台「运行日志」页（`/admin/logs`）：读 API 进程内存环形缓冲（最近 2000 条、
INFO 起、含 `oj.http` 的 >=400 请求与未捕获异常栈），支持级别/关键词筛选与游标翻页。
它是「进程内实时快照」，容器重启即清空且不落盘；要看历史留存仍以 `docker logs deploy-oj-api` 为准。

### 8.4 HTTPS 上线（预留，建议尽快）

nginx 配置文末有 443 注释模板：证书（certbot 或云厂商）挂载进 web 容器后按模板启用，
并将 /oj/api/ 的 `X-Forwarded-Proto` 改为 https。

### 8.5 容器命名与迁移（2026-09 起）

项目专属服务一律显式命名 `deploy-oj-<服务名>`；可复用基础设施（postgres / redis / minio）
不设 `container_name`，继续用 compose 自动名 `deploy-<服务>-1`，便于其他项目复用同一套基础设施：

| 服务 | 容器名 | 类型 / 定义位置 |
|---|---|---|
| web | `deploy-oj-web` | 项目专属 · `deploy/compose.prod.yml`（仅生产有 web 容器） |
| api | `deploy-oj-api` | 项目专属 · `deploy/compose.prod.yml` |
| judge-node | `deploy-oj-judge-node` | 项目专属 · `deploy/docker-compose.yml`（dev/prod 同名） |
| assistant-node | `deploy-oj-assistant-node` | 项目专属 · `deploy/docker-compose.yml`（dev/prod 同名） |
| postgres | `deploy-postgres-1` | 可复用基础设施（自动名，无 `container_name`） |
| redis | `deploy-redis-1` | 同上 |
| minio | `deploy-minio-1` | 同上 |

按名字操作容器：

```bash
docker logs -f deploy-oj-api                          # API 历史日志（旧写法 docker logs api 无效）
docker exec -it deploy-oj-api sh                      # 进 API 容器排查
docker exec -T deploy-postgres-1 psql -U oj -d oj     # 基础设施仍是自动名
docker ps --format 'table {{.Names}}\t{{.Status}}'
```

`docker compose` 系列命令（`ps` / `logs` / `exec` / `restart`）仍按**服务名**寻址，不受改名影响。

改名影响与注意：

- **旧容器不会自动消失**：改名前的 `deploy-web-1` / `deploy-api-1` / `deploy-judge-node-1` /
  `deploy-assistant-node-1` 与新容器会并存，旧 web 容器还占着 80 端口。首次上线前须先删掉它们
  （命令见 §5；`deploy/update.sh` 已内置，`deploy-remote.sh` 第一步先 `down` 也可清掉）。
- **数据完全不受影响**：只重建容器、不动卷；卷名与项目名绑定，容器改名不影响 `pgdata` /
  `redisdata` / `miniodata`。切勿加 `-v`。
- **`-p <project>` 不再是隔离手段**：显式 `container_name` 全局唯一、不带 project 前缀，本机想用
  `-p ojprod` 并行再起一套生产栈会与 dev 栈重名冲突，必须先把 dev 栈 `stop` 掉（见 docs/环境搭建记录.md）。
- **对外形态不变**：仍只有 web 容器发布 80，api / infra 端口一律 127.0.0.1。
- **改完自检**：`docker compose -f docker-compose.yml -f compose.prod.yml config` 输出中，
  web / api / judge-node / assistant-node 应带 `container_name: deploy-oj-*`，infra 三个不应有该字段。

## 9. 常见问题

| 现象 | 处理 |
|---|---|
| 拉镜像超时 | 配加速器（§2.4） |
| minio 报 `denied` | MinIO 已删 Docker Hub 镜像，别用 `minio/minio:latest`；compose 已用 `quay.io/minio/minio:latest`，拉不动换 §2.4 的代理缓存 |
| judge-node 起不来 | 服务器不支持 privileged 容器（换 KVM 类主机） |
| 判题 500 / 一直 waiting | `curl /oj/api/health/judges` 看 online_nodes，比对 judge-node.env 与 api.env 令牌是否一致 |
| 访问根路径被 302 | 属预期：站点在 `/oj/` 子路径下，根路径统一 302 到 `/oj/`（含子路径） |
| AI 助手无流式/504 | 确认 nginx 的 `proxy_buffering off` 与 900s 超时未被改动 |
| 改 api.env 后 postgres/minio 密码不生效 | 密码仅在卷**首次初始化**时生效，改密码需 `docker compose ... down -v` 删卷重建（会清空数据） |
| 端口 80 被占 | `sudo lsof -i:80` 找到占用进程，或改 compose.prod.yml 的 `80:80` 为其他端口（域名解析不变） |
| judge-node 构建慢 / 每次都装 apt | 判题依赖已下沉到基础镜像（§5.1），日常重建只走上层。报 `oj-judge-base:24.04` 找不到时，先执行 §5.1 的构建命令 |
| 更新后 web 起不来 / 报 `port 80 already allocated` | 改名前的旧容器（`deploy-web-1` 等）还在运行占着端口。按 §5 先 `docker rm -f` 掉 4 个旧专属容器，再 `up -d --build`（走 `deploy/update.sh` 已自动处理） |
| `docker logs api` 报 No such container | 容器名不是服务名：按服务名用 `docker compose ... logs api`，或按容器名 `docker logs deploy-oj-api`（§8.5） |
| 本机 `-p ojprod` 起生产栈报名字冲突 | 专属服务是显式容器名、不受 project 前缀隔离：先 `docker compose stop` 停 dev 栈（§8.5、docs/环境搭建记录.md） |
