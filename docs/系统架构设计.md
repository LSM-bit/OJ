# OJ 系统架构设计

> 参考产品：牛客 OJ（页面/交互）、QOJ / Codeforces（赛制规则）。


**核心设计决策——计算节点主动外连**（判题与 AI 助手同构）：
- judge-node / assistant-node 容器均**不开放任何入站端口**，启动后主动向各自网关发起 gRPC 双向流（`Connect`）并长期挂住；
- 网关有任务时经该流下发（`SubmitJob` / `ChatJob`），节点做完经同一流回传（`JudgeResult` / `ChatDelta·ChatDone`）；
- 优点：节点可以藏在 NAT/内网/家用宽带后，横向扩容零配置；网关单点只做调度不做执行，爆炸半径小；
- AI 助手的**权限边界**由此天然成立：工具执行全在 API 侧，节点只做模型 I/O、零 DB/存储访问，Anthropic key 只存节点 env。

### 1.2 技术栈

## 2. 核心横切机制

### 2.1 雪花 ID 与前端精度

- 所有表主键为**应用层雪花 ID**（`utils/snowflake.py`）：1bit 符号 + 41bit 毫秒时间戳 + 10bit 机器 ID + 12bit 序列号，Lock 保护线程安全，时钟回拨 ≤5ms 等待、否则抛错。
- 雪花 ID 超出 JS `Number.MAX_SAFE_INTEGER`（2^53-1），两端配合：
  - 后端：全局默认响应类 `BigIdJSONResponse` 递归把大整数转字符串；
  - 前端：axios 拦截器用 json-bigint（`storeAsString`）解析；回传字符串 ID，Pydantic 自动 str→int。
- 对外另有 `display_id`（题目自增展示号），避免把雪花 ID 暴露在 URL 观感上；题号跳转、随机选题、`?did=` 精确查全部基于 display_id。

### 2.2 认证与权限（详见《权限模型设计.md》）

- **认证**：JWT Bearer（7 天有效），`services/auth.py` 提供三级依赖：
  - `CurrentUser`（强制登录）、`get_optional_user`（未登录返回 None，浏览类接口用）、`require_admin`（`/admin/*` 整组挂载）。
  - 登录时校验 `banned`，封禁账号即使持有旧 token 也会 401。
- **角色**：全局仅 `USER / ADMIN`；出题、建赛、建题单全部放开给登录用户。
- **资源级权限**（`services/access.py`）——题目/比赛/题单共用一套四条规则：
  1. `is_public=true`；2. 本人所有；3. 团队所有且是成员；4. ADMIN。管理权 = 本人 / 团队队长副队 / ADMIN。
- **比赛管理权**（`_is_manageable`）：创建者 / 团队队长副队 / ADMIN——编辑比赛、发比赛公告、批量重测、看全部提交记录与详情都基于它。
- **间接授权特例**：题目在题单/比赛内时，可见性**只看载体**——能进比赛的人，比赛内题目（含私有题）全部可见。请求通过 `?playlist_id=` / `?contest_id=` 携带载体上下文（`services/access_deps.py`）。
- **防枚举**：私有资源对无权者一律 404"资源不存在"（与不存在同响应）。

### 2.3 存储抽象（services/problem_data.py）

测试数据与头像不直接碰 `Path`，全部经模块级 async 原语，按 `settings.storage_backend` 分派 `MinioStore` / `LocalStore` 双后端：

| 原语 | 用途 |
|---|---|
| `read_file / read_text_file(pid, version, rel)` | 题面样例展示、用例预览、验证标程读期望输出 |
| `read_manifest / write_manifest(pid, version, ...)` | 用例增删时改写清单 |
| `append_files(pid, version, files)` | 增量覆盖（追加样例用例） |
| `write_problem_data(pid, version, files)` | 整体替换（上传 zip；manifest 合法性**内存校验**后再写，MinIO 无目录 rename，逐对象覆盖） |
| `iter_problem_data(pid, version)` | 网关 `FetchProblemData` 流式下发（list_objects + get_object） |
| `put_avatar / get_avatar / delete_avatar` | 头像三操作，`oj-avatars` 公共桶 |

- MinIO SDK 是同步的，统一 `asyncio.to_thread()` 包装，不卡事件循环；`MinioStore` 启动时幂等 `make_bucket`。
- **判题节点零感知**：节点经 gRPC 流拉数据并缓存本地，不关心网关背后介质。
- **头像 URL 不变**：`main.py` 不挂 StaticFiles，改为代理端点 `GET /static/avatars/{filename}`（按扩展名给 content-type，1h 缓存头），已存库的头像路径无需迁移、前端零改动。
- 测试（conftest）强制 `local` 后端，测试基建不依赖 MinIO。

### 2.4 判题协议（api/protos/judge/v1/judge.proto）

两组 RPC：

| RPC | 方向 | 说明 |
|---|---|---|
| `Connect(stream NodeMessage) returns (stream ServerMessage)` | 节点 ↔ 网关 | 双向流：注册/心跳/结果上行，ack/任务下行 |
| `FetchProblemData(ProblemDataRequest) returns (stream FileChunk)` | 节点 → 网关 | 测试数据分块流（256KB/块），`x-node-token` 元数据认证 |

信封 oneof：
- `NodeMessage`: `Register | Heartbeat | JudgeResult | RunCodeResult`
- `ServerMessage`: `RegisterAck | SubmitJob | CancelJob | RunCodeJob`

`SubmitJob` 关键字段：`submission_id / language / code(bytes) / ResourceLimits(time_ms, mem_mb, output_kb, process, cores) / problem_id / data_version / cases[] / stop_on_failure`。

`data_version` 是缓存失效锚点：题目重新上传数据即换版本号，节点本地按 `{problem_id}-{data_version}` 目录缓存，旧版本自然淘汰。

### 2.5 AI 助手协议（agent/protos/assistant/v1/assistant.proto）

单组 RPC，与判题协议**分文件**（消息演进节奏不同）：

| RPC | 方向 | 说明 |
|---|---|---|
| `Connect(stream NodeMessage) returns (stream ServerMessage)` | 节点 ↔ 助手网关 | 双向流：注册/心跳/模型增量上行，任务/工具结果/取消下行 |

信封 oneof：
- `NodeMessage`: `Register | Heartbeat | ChatDelta | ChatDone | ChatError`
- `ServerMessage`: `RegisterAck | ChatJob | ToolResult | CancelChat`

`ChatJob` 关键字段：`job_id / model / system / messages_json / tools_json / max_tokens`——**会话消息与工具入参/结果整体走 JSON 字符串字段**（Anthropic blocks 原样），proto 保持薄，改工具不必重编协议。`ChatDone.content_json` 携各轮全量 assistant blocks（落库回放用）+ 累计 usage + `stop_reason(end_turn/max_tokens/max_turns/timeout)`。

与判题链路的三点差异：

1. **工具执行在网关侧闭环**：节点上行 `ChatDelta(tool_use)` 后挂起该 tool_use 的 Future，API 侧 `execute_tool`（权限在此强制）后经 `ToolResult` 回填唤醒，节点组下一轮——一次 `/assistant/chat` 内可来回 8 轮；
2. **流式不攒段**：`text_delta` 逐 token 上行 → 网关事件队列 → SSE 即时透传浏览器；
3. **节点无状态**：不落库、不读存储，重启只丢在途对话（历史在 API 侧三表里）。

生成代码两处使用：`api/app/assistant_gateway/gen/`、`agent/assistant_node/gen/`（生成命令见《环境搭建记录.md》）。

## 3. 模块划分：可执行操作与流程

以下按模块逐一列举对外可执行操作（REST 端点 + 权限），并给出核心操作的执行流程。

### 3.1 用户模块（routers/users.py，前缀 `/`）

| 操作 | 端点 | 权限 |
|---|---|---|
| 注册 | `POST /register` | 公开 |
| 登录 | `POST /login` | 公开（封禁账号 403） |
| 查看自己 | `GET /me` | 登录 |
| 编辑资料（用户名/邮箱/改密码） | `PATCH /me` | 登录 |
| 上传/删除头像 | `POST|DELETE /me/avatar` | 登录（存储走 `put_avatar/delete_avatar`） |

**登录流程**：
```
用户名+密码 → bcrypt 校验 → banned 检查 → 签发 JWT(sub=user.id, role)
           → 前端存 localStorage，后续请求带 Authorization: Bearer
```
**改密码流程**：请求带 `old_password` + `new_password` → 校验旧密码 → 更新 hash（不支持"改密后全端下线"，一期不做 token 撤销）。

### 3.2 题目模块（routers/problems.py，前缀 `/problems`）——三步出题

| 操作 | 端点 | 权限 |
|---|---|---|
| 题目列表（分页 + 搜索 + 标签交集 + 归档视图） | `GET /problems`，参数见下 | 可选登录 |
| 标签云（公开题标签计数降序，排除归档题；同题重复标签只计一次） | `GET /problems/tags` → `{items:[{tag,count}]}` | 公开 |
| 标签实例搜索 / 新建（弹窗选择用） | `GET /problems/tags/search?q=` / `POST /problems/tags` | 搜索公开；新建登录（重名幂等） |
| 题目详情 | `GET /{problem_id}`（可带 `?playlist_id=|contest_id=` 间接授权） | 载体可见 |
| 创建草稿 | `POST /problems` | 登录（个人或团队） |
| 编辑题面/配置 | `PUT /{problem_id}` | 管理权 |
| **上传数据包** | `POST /{problem_id}/data`（zip：成对 *.in/*.out，manifest 由服务端生成） | 管理权 |
| 用例列表 / 加样例 / 删用例 | `GET /{id}/cases`、`POST /{id}/cases/sample`、`DELETE /{id}/cases/{idx}` | 管理权 |
| **标程验证** | `POST /{problem_id}/verify` | 管理权 |
| **发布/撤回** | `PUT /{problem_id}/publish` | 管理权 |
| **归档/恢复** | `PUT /{problem_id}/archive` body `{archived: bool}` | 管理权 |

**列表参数语义**（`GET /problems`）：
- `mine=0` 刷题视角（公开题）/ `mine=1` 出题视角（我拥有 + 我团队的，含草稿；ADMIN 全量）；
- `page/size` 分页（size 上限 1000）；`full=1` 返回 `{total, items}`（分页页用），默认裸数组（兼容旧调用方）；
- `q=关键词` 标题 ilike 模糊搜，纯数字时同时主题号（模式串先剥 `%_\` 防通配注入）；
- `did=N` 按题号精确查——题号跳转与随机选题走它，不受当前分页限制、全库可达；
- `tag=模拟,数学` 多标签交集：PG 走 JSONB `@>` 包含（数组字面量经 json.dumps 转义 + 单引号翻倍防 SQL 字面量逃逸），SQLite 降级为转义 LIKE；
- `archived=1` 仅看归档题（仅 `mine=1` 视角有效）；默认一律排除归档题。

**三步出题流程**（前端 ProblemEditView 按步骤引导）：
```
① 创建草稿：标题/题面(MD+LaTeX)/难度/标签（弹窗从 tags 表实例搜索选择，可现场新建）
   /时限内存 → is_public=false
② 上传数据：zip 解压 → pack_cases() 只取成对 .in/.out（杂物/自带 manifest 丢弃），
   自然序重排，sample* 前缀视为样例（0 分）、隐藏用例平分 100 分，服务端生成 manifest
   → write_problem_data() 按存储后端落 MinIO（或本地盘）
   → bump data_version（节点缓存自动失效）
③ 标程验证：POST /verify 提交标程 → 网关下发 SubmitJob(stop_on_failure=false)
     节点跑完全部用例 → 逐点比对（与判题同一套 _same_output 规则）
     全部通过 → 标程与 verified_at 写入 problem.config（发布凭证）
④ 发布：PUT /publish {is_public:true} → 硬校验（有数据 + verified_at 存在）→ is_public=true
```

**归档语义**（`archived` 字段，出题中心归档/恢复按钮）：归档题不出现在任何题目列表（公开视角与管理视角默认均排除，标签云也不统计）；详情仍可访问（已有引用不失效）；**归档后不可再提交**（`POST /submissions` 400「题目已归档」）；`?mine=1&archived=1` 只看归档题，可随时恢复。

**提交判题全流程**（系统主链路）：
```
POST /submissions
  → 权限：is_public？否则走题单间接授权 / 出题人本人

  → await gateway.submit(job, timeout=120)      ← 请求挂起等结果（高峰由网关排队）
       网关：pending[submission_id]=Future → _dispatch()
             有空闲节点(capacity 未满) → 下发；否则进 waiting_jobs 队列
       节点：semaphore 限并发 → _ensure_data（本地缓存命中？否则流式拉取）

             → 聚合（最严重状态/总分/最大耗时内存）→ 经 bidi 流回传
       网关：_resolve() set Future → _try_redistribute() 补位队列任务
```

### 3.4 判题网关（api/app/judge_gateway/，随 API 进程启动在 :50051）

对上（REST 路由）暴露：`submit(job)`、`run_code(job)`、`snapshot()`（后台节点监控用只读快照）。

**节点生命周期**：
```
Connect bidi 流建立 → 首条消息必须是 Register(token 在网关配置白名单内)
  → 建 Node{out_stream 队列, capacity, running} → 回 RegisterAck
  → 之后每条上行消息刷新 last_seen；result/run_code_result 使 running-1 并触发调度
流断开 → 节点摘除 → 其 in-flight 任务由 pending Future 超时兜底（路由层 120s 超时返回 se）
```

**调度策略**：轮询找 `running < capacity` 的在线节点直接下发；无空闲进 `waiting_jobs` deque，任何节点回传结果时 `_try_redistribute()` 立即补位。`pending: dict[submission_id → Future]` 是网关的核心状态；`result_sink` 回调为主动推送模式（重判等不经过 HTTP 挂起的场景预留）。

### 3.5 判题节点（judge/judge_node/）

**daemon.py** —— 主循环与聚合：
```
run(): 连接 → 服务 → 断开后指数退避重连（1s→2s→4s…封顶 30s；注册成功即重置）
  上行流：首条 Register + outbox 队列（心跳每 10s：running_tasks）
  收到 job → asyncio.create_task(_execute_job)（不阻塞收流）
  _execute_job: semaphore(capacity) → _judge_inner → 回传
_judge_inner: 拉数据 → 构造 JudgeCase → to_thread(execute_cases)（不卡事件循环）
  → 聚合：STATUS_HIGHEST_SEVERITY 取最严重测试点状态
          (ce > se > tle > mle > ole > re > wa > ac)
  → score = 通过测试点分值之和；time/mem 取各点最大值
  → ce/re 附带 stderr（截断 8KB）帮助定位
```

**executor.py** —— nsjail 沙箱执行：
- 编译一次（时限 = 10× 题时限、内存 ≥4GB、进程 ≥512——javac/JVM 需要大地址空间与进程配额），失败则整题 `compile_error`。
- 逐测试点运行：`nsjail --config /etc/oj/nsjail.cfg`（全 namespace 隔离 net/user/ns/pid/ipc/uts，nobody(65534) 运行）+ `--rlimit_as/--rlimit_fsize/--rlimit_nproc/--time_limit`。
- **内存计量**：`_RssSampler` 后台线程每 2ms 沿 `/proc/<pid>/task/<pid>/children` 逐层采样进程树 VmHWM 取峰值（程序退出后 /proc 即消失，必须边跑边读；nsjail 自身 ~8.5MB 不计入）。
- **状态分类规则**（实测校准的退出码表，`_run()` 尾部）：

| 现象 | 判定 |
|---|---|
| 超出 stdout 上限（rlimit_fsize） | `output_limit_exceeded` |
| 外层墙钟兜底超时（时限+10s） | `time_limit_exceeded` |
| exit 0 且输出匹配 / 不匹配 | `accepted` / `wrong_answer`（忽略行尾空格与末尾换行） |
| 编译阶段非零退出 | `compile_error` |
| exit 137/143/-9/-15（nsjail 按 --time_limit SIGKILL 子进程后自身退出码） | `time_limit_exceeded` |
| exit 134/-6（SIGABRT）且 stderr 含 bad_alloc/MemoryError | `memory_limit_exceeded` |
| exit 134/-6 其余（C++ 未捕获异常） | `runtime_error` |
| exit 1 + stderr 含 MemoryError / std::bad_alloc / Cannot allocate memory | `memory_limit_exceeded` |
| exit 1 + stderr 含 SyntaxError / IndentationError（Python 语法错运行期才暴露） | `compile_error` |
| 其余（含段错误 exit 139） | `runtime_error` |

- **Java 特例**：JVM 预留虚拟地址空间远大于实际内存，运行期 `rlimit_as` 放宽到 4GB，真实内存靠 `-Xmx256m` + VmHWM 计量兜底。

**datacache.py** —— 题目数据缓存：`{problem_id}-{data_version}` 目录 + `manifest.json` 存在性判定；同步时先写 `.tmp`，完整落盘（含 manifest 校验）后原子 rename；访问刷新 mtime 供 LRU 清理。

| 操作 | 端点 | 权限 |

| 比赛详情（含题目及每题时限） | `GET /contests/{id}` | 比赛可见 |
| **编辑比赛**（改 start_at/end_at/board_freeze_minutes） | `PATCH /{id}` | 比赛管理权（**归档前**可改） |
| 报名 | `POST /{id}/register` | 登录 |
| **创建重现赛（VP）** | `POST /{id}/vp` | 比赛可见 + 登录 |
| 排行榜 | `GET /{id}/standings` | 比赛可见 |
| **比赛内提交** | `POST /{id}/problems/{alias}/submit` | 开始后即可；进行中须已报名 |
| **比赛公告列表 / 发布** | `GET` / `POST /{id}/announcements` | 列表比赛可见；发布需管理权 |
| **按题批量重测** | `POST /{id}/problems/{alias}/rejudge` | 比赛管理权（结束前） |
| **比赛提交记录**（所有人） | `GET /{id}/submissions` | 管理者看全部；其他人只看自己的 |
| **比赛提交详情**（源码/测试点明细/错误信息） | `GET /{id}/submissions/{submission_id}` | 本人 / 比赛管理者，其余 404 防枚举 |

**归档规则（派生状态，不落库、无迁移）**：比赛结束满 24 小时（`ARCHIVE_AFTER_END`）自动视为归档，`archived = now > end_at + 24h` 随 `end_at` 实时派生，改时间即顺延归档时刻。归档后：
- **不能再编辑**比赛信息（`PATCH /{id}` 400）；
- **仍可提交练习**——比赛内提交时间窗从"仅进行中"放宽为"开始后均开放"，进行中必须报名，结束后/归档后对比赛可见者开放（注意：结束后提交同样计入榜单重放，前端提交面板有 alert 提示）；
- **可创建重现赛**。
- 前端列表按 `archived` 分「未结束 / 已结束（归档）」两桶（替代旧的三分法），卡片仍显示细粒度 phase 标签 + 归档角标。

**重现赛（VP）流程**（`POST /{id}/vp`）：复制原赛题目（含 alias）与标题/简介/赛制，新建一场归属**当前用户**的比赛——时间窗缺省"立即开始、时长与原赛相同"（可自定，结束须晚于开始），默认**私有**、**不封榜**，创建者自动报名；原比赛任何阶段（含已归档）都可 VP。响应带 `vp_of=原赛 id`。

**创建流程（前端两步向导）**：第一步 `ContestEditView` 填基本信息（标题/赛制/时间/封榜/归属/可见性）→ 草稿存 `sessionStorage(contest_new_draft)` → 第二步 `ContestProblemPickView` 独立选题页（公开/我的两个视角、标签多选交集、题号/标题搜索、分页；已选题按 A/B/C 顺序、可移除、可空手创建）→ 携带 `problem_ids` 调 `POST /contests`。
后端校验：结束时间晚于开始时间；可添加"我可见"的任意题目（**他人私有题 403**，防借比赛泄露私有题）；alias 按顺序 A/B/C…。

**防打表**（覆盖三处）：
- 比赛进行中 `GET /contests/{id}` 返回 `detail=[]`（题目信息只有 alias/标题/时限）；
- 比赛内提交响应与提交列表，进行中 `detail` 恒为 `[]`；
- **提交详情**按 `full = 管理者 or 比赛已结束` 控制：`full` 才返回测试点明细；`error_message` 在 `full or 状态==CE` 时返回（CE 错误信息不含测试数据，对本人始终可见，帮助选手修编译错）。源码本人与管理者随时可见。

**比赛管理**：`PATCH /{id}` 改时间/封榜（归档前）；`POST /{id}/announcements` 发比赛公告；`POST /{id}/problems/{alias}/rejudge` 对该题全部比赛提交批量重测（结果走 result_sink 落库，不经过 HTTP 挂起）。

**榜单计算**（services/standings.py，`compute_standings`）：拉取该比赛全部提交按时间升序**逐条重放**，生成每题 cell `{alias, attempts, solved, solve_time, pending, frozen}`：
- ACM 罚时 = Σ(过题时刻 + 20 × 过题前错误次数)；**过题确认后的错误提交不计罚时**（标准 ACM 规则）；
- **封榜**（`board_freeze_minutes`）：进入封榜窗口后的提交——过题显示 `frozen`（前端气泡 "?"，不进 solved 数），错误提交计 `pending`；
- OI 按分数；排序：ACM (-solved, penalty)，OI (-score, penalty)。

```
  → 落库 user 消息（标题兜底 message[:30]）
  → ChatJob(system=_build_system(ctx), tools=TOOL_SPECS(+REVIEW_TOOL_SPECS if ctx.review), ...)
  → _event_stream：网关事件 → SSE text_delta/tool_start/tool_result/done/error
       tool_use → execute_tool（权限强制 + <tool_data> 8KB 包裹 + AssistantToolCall 审计）→ 回填网关
  → done：assistant 消息落库（tool_use 块并入 done/is_error 状态）+ usage
  → 首轮异步挂 _summarize_title（零工具小请求，≤14 字标题，异常静默）
```

工具面与安全红线详见《AI助手Agent设计.md》§5/§7。

## 4. 数据模型（20 张表）

```
users ─┬─< submissions >─┬─ problems ─< testcases
       │                 │      ↑ (problem_id 被 contest_problems / playlist_problems 引用)
       │    contests ─┬─< contest_participants >─ users
       │              ├─< contest_problems
       │              └─< contest_announcements(author)
       ├─< team_members >─ teams
       ├─< playlist_problems >─ playlists
       ├─< checkins        notifications / discussions（预留）
       ├─< announcements(author)        tags（标签实例，题目引用其名字）
       └─< assistant_conversations ─< assistant_messages
                        └─< assistant_tool_calls(user_id/conversation_id 双维度)
```

| 表 | 要点 |
|---|---|
| `users` | role(USER/ADMIN)、rating(1500 起步)、avatar、banned |
| `problems` | display_id 展示号、tags JSONB 数组（`?tag=` 筛选：PG `@>` 包含 / SQLite LIKE 降级）、config JSONB（时限/内存/data_version/标程凭证）、owner_type+owner_id 多态（user/team）、is_public、archived（归档不出列表、不可提交） |
| `tags` | 标签实例表（name 唯一）：出题时弹窗搜索选择、搜不到可新建；题目仍以标签名数组存储 |
| `testcases` | (problem_id, idx) 唯一、case_id 对应数据包文件名、is_sample（样例题面可见）、可单点覆盖时限 |
| `submissions` | contest_id 可空区分比赛提交、code 留存支持重判、detail JSONB 存逐点结果、status 枚举 waiting/judging/ce/wa/tle/mle/re/ole/ac/se |
| `contests` | rule(acm/oi/ioi)、board_freeze_minutes、owner 多态、status；**归档不落库**——结束后满 24h 由 end_at 派生 |
| `contest_participants` | (contest_id, user_id) 唯一 |
| `contest_problems` | alias A/B/C |
| `contest_announcements` | 比赛公告（contest_id CASCADE）：比赛管理者发布，仅比赛页内可见（与全站 announcements 区分） |
| `teams` / `team_members` | role(owner/admin/member)，(team_id, user_id) 唯一；teams.archived（归档隐藏/禁加入） |
| `playlists` / `playlist_problems` | idx 排序，(playlist_id, problem_id) 唯一 |
| `announcements` / `checkins` | 置顶标记 / (user_id, day) 唯一 |
| `assistant_conversations` | context JSONB（problem/submission/problem_review）、title 自动摘要（兜底首条消息 30 字）、**archived 软删**（用户删除=归档，后台留存） |
| `assistant_messages` | content JSONB = Anthropic blocks 原样（tool_use 块落库时并入 done/is_error 状态）；token 用量落 assistant 行；user 行按日 count 作对话配额 |
| `assistant_tool_calls` | (user_id, tool, created_at) 流水：run_on_sample 日配额计数 + 全量审计 + ADMIN 看板工具分布 |

所有主键雪花 ID（BigInteger，Python 端 `default=snowflake_pk` 生成）；迁移由 Alembic 管理，14 个版本、单 head `dd44ee55ff66`（助手会话归档列）。

## 6. 部署拓扑（deploy/docker-compose.yml）

```
postgres:16-alpine  :5432  (healthcheck pg_isready, volume pgdata)
redis:7-alpine      :6379  (预留，未强依赖——配额/榜单均走 DB)
minio               :9000 S3 API / :9001 Console (volume miniodata, 桶 oj-problems/oj-avatars)
judge-node          (build judge-node.Dockerfile, privileged)
                      SERVER_ADDRESS=host.docker.internal:50051
                      SERVER_TOKEN=dev-judge-token
                      restart=unless-stopped；无端口映射（纯外连）
assistant-node      (build assistant-node.Dockerfile, 非 privileged——无沙箱需求)
                      SERVER_ADDRESS=host.docker.internal:50060
                      SERVER_TOKEN=dev-assistant-token
                      env_file: .env 注入 ANTHROPIC_API_KEY（勿用 compose 内联 ${VAR}，
                        会被宿主 shell 提前插值成空串——实测教训）
                      # ASSISTANT_MOCK=1 注释行保留，无 key 联调时打开
                      restart=unless-stopped；无端口映射（纯外连）
api   本地 venv 运行 :8000（生产容器化，nginx 反代）
web   vite build → nginx 静态托管
```

**运维注意**：
- judge-node / assistant-node 代码**不是 bind mount**，更新需 `docker cp` 进容器后 `docker restart`，等 ~12s 看 `/health/judges` 确认重连；
- 判题节点需 `privileged`（nsjail 需要 user/net namespace 操作能力）；助手节点不需要；
- **改表必与重启同批**：`alembic upgrade head` 后必须重启 API——uvicorn `--reload` 只重载代码不跑迁移，新表/新列查不到（实测「连接中断」根因之一）；
- 敏感配置走环境变量：`JWT_SECRET`、`JUDGE_GATEWAY_TOKENS`、`ASSISTANT_GATEWAY_TOKENS`、`ANTHROPIC_API_KEY`（仅助手节点）、`OJ_SNOWFLAKE_NODE_ID`（多实例必配且互不相同）、`MINIO_*`（dev 默认值为占位凭证，生产必改）；
- 题目测试数据与用户头像存 MinIO（`storage_backend=minio` 默认）：`oj-problems` 桶 key 为 `{problem_id}-{data_version}/manifest.json` 与 `cases/tc{N}.in/.out`，`oj-avatars` 桶存头像；判题节点经 gRPC `FetchProblemData` 流式拉取并缓存到节点本地 `/cache`，不感知网关后端介质；`storage_backend=local` 退回本地磁盘 `data/problems/`（pytest 用）。存量磁盘数据用 `api/app/scripts/migrate_problem_data_to_minio.py` 一次性搬迁（幂等可重跑）；
- 比赛归档为**派生状态**（end_at + 24h），无后台任务、无迁移——改比赛时间即自动调整归档时刻。

## 7. 已知边界与后续演进

| 项 | 现状 | 方向 |
|---|---|---|
| 提交响应模式 | HTTP 挂起等结果（timeout 120s） | 改为落库 waiting + WebSocket 推送，解耦长连接 |
| SPJ 特判 | proto 已留 `spj` 字段 | 节点加载 checker 程序回填分数 |
| 取消判题 | proto 有 CancelJob，节点暂忽略 | 支持"比赛中撤回错误提交"类场景 |
| 榜单刷新 | 前端手动/提交后刷新 | 定时轮询或 WebSocket |
| 邀请码 | 进程内存，重启失效 | 落库 + 过期时间 |
| Rating | 字段预留（1500 起步） | 比赛结束后按 Elo/Codeforces 公式结算 |
| 讨论区/通知 | 表已建，路由未开 | 后续阶段 |
| 提交源码存储 | 存 DB（code TEXT 列） | 迁对象存储（同 oj-problems 模式）+ 生命周期策略 |
| 赛后练习提交 | 计入榜单重放（与正式提交同权重） | 可为 `archived` 赛加"练习不计数"标记，重放时过滤 |
| 随机选题 | 前端取最大题号后随机 did 逐个试跳（≤20 次） | 后端 `GET /problems/random` 一条 SQL 直接返回 |
| 题目列表 full 模式 | `total` 用 `count(*)` 子查询再取页 | 数据量大后改估算或窗口函数 |
| 助手节点负载 | 网关按 capacity 轮询，单节点也够用 | 多 assistant-node 外连即横向扩容（协议天然支持） |
| 诊断深度 vs 数据保密 | 学生面只给逐点 status；审校面 8 条截断预览（受控例外） | 「失败点输入规模特征」脱敏形式可二期再评估 |
| 代写检测 | prompt 约束 + 全量落库抽查 | 相似度检测已评估砍掉；如需可回补静态检测 |
