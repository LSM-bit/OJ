# 权限模型：公有/私有资源 + 团队 + 路由权限认证（已实现）

> 编写日期：2026-09-07（设计稿）｜ 最近更新：2026-09-16（阶段 8 落地后现状纪实）
> 状态：**已实现**——本文原为设计稿，现按实际落地情况重写；与设计稿的差异在 §8 汇总

---

## 1. 目标（兑现情况）

1. **题目 / 比赛 / 题单**三类核心资源都区分公有（public）与私有 ✅
2. 用户可以组成**团队**（发起人=队长），资源归属「个人 / 团队」 ✅
3. 所有权限校验**收敛到服务层 + 路由依赖工厂**（`services/access.py` + `services/access_deps.py`），业务路由不写散落的 if ✅
4. 一条统一的**资源可见性判定规则**，题目/比赛/题单共用 ✅

## 2. 可见性判定规则（核心，已按此实现）

资源 R（题目/比赛/题单）对用户 U 可见，当且仅当满足其一（`can_view`，access.py:29）：

```
1. R.is_public = true                           （公有资源，所有人可见）
2. U.role = ADMIN                               （管理员全量可见）
3. R.owner_type = 'user' 且 R.owner_id = U.id   （个人私有资源）
4. R.owner_type = 'team' 且 U 是该团队成员       （团队资源，任何成员可见）
```

未登录用户（user=None）只能看到公有资源。

### 2.1 三类资源归一化 ✅

题目、比赛、题单共用同一组归属字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `owner_type` | Enum(`user` / `team`) | 归属个人或团队（默认 `user`） |
| `owner_id` | BigInteger | user.id 或 team.id，由 owner_type 消歧 |
| `is_public` | Boolean | 公有/私有 |

### 2.2 私有题目通过比赛/题单间接可见 ✅（实现比设计更收敛）

设计稿设想「反查宿主资源」，实际实现为**载体上下文参数**（access_deps.py:52 `problem_view_allowed`）：

- 题目详情/做题路由接受可选 query 参数 `?playlist_id=` / `?contest_id=`；
- 只要该载体对当前用户可见（`can_view` 判载体本身）**且**题目确实在该载体内（查 `playlist_problems` / `contest_problems`），题目即可见——**无论题目自身 `is_public` 与否**；
- 即「题目在赛内/题单内只看载体」：题面公开性与宿主解耦，避免不公开的题目因入榜泄露；
- 不带载体参数时，回落到 §2 四规则判题目自身。

### 2.3 读权限与写权限分离 ✅

| 操作 | 判定函数 | 允许的人 |
|---|---|---|
| 读（题面/榜单/题单内容） | `can_view` | §2 四规则 |
| 写（编辑资源、上传数据、审校工具面） | `can_manage`（access.py:46） | 个人资源=owner 本人；团队资源=队长(`owner`)/副队长(`admin` 团队角色)；ADMIN |
| 提交 | 可见性 + 比赛场景需已报名 | |
| 团队管理操作 | `require_team_manage`（队长/副队/ADMIN，否则 403） | |

## 3. 角色体系（与设计稿的最大差异）

**全局角色只有两级**：`UserRole = USER / ADMIN`（models/\_\_init\_\_.py:35）。

- 设计稿预设的四级角色（USER / PROBLEM_SETTER / CONTEST_ADMIN / ADMIN）**未采用**——迁移 `d1e2f3a4b5c6` 将四级收敛为两级；
- 决策依据：出题、建赛、建题单对所有登录用户放开（资源级权限已足以约束"只能管自己的"），中间角色形同虚设，反而增加 ADMIN 改角色下拉与文档解释成本；
- 团队内部角色（owner / admin / member，`TeamRole`）是**资源维度**权限，与全局角色正交，保留三级。

判定写权限时的合流逻辑（`can_manage`）：全局 ADMIN 放行 → `owner_type=user` 比 owner_id → `owner_type=team` 查 `get_team_role` 是否 owner/admin。

## 4. 后端实现（落地形态）

### 4.1 统一权限服务层 ✅ `api/app/services/access.py`

```python
can_view(db, user, owner_type, owner_id, is_public) -> bool   # §2 四规则；user 可为 None
can_manage(db, user, owner_type, owner_id) -> bool            # 写权限
get_team_role(db, team_id, user_id) -> TeamRole | None        # 团队成员角色
require_team_manage(db, team_id, user)                        # 不通过抛 403
```

### 4.2 路由依赖工厂 ✅ `api/app/services/access_deps.py`

`ProblemAccess("view"|"manage")` / `ContestAccess(...)` / `PlaylistAccess(...)` 三个工厂：加载资源 → 判权限 → 返回 ORM 对象，业务路由签名里 `p: Problem = Depends(ProblemAccess("view"))` 即完成鉴权。

- **私有资源一律 404**（`_deny()`，与「不存在」同响应，防枚举探测）；未登录访问 manage 操作先 401；
- view 版工厂额外接受 `playlist_id` / `contest_id` 上下文参数（§2.2）；
- 用户身份沿用 `services/auth.py` 的 `CurrentUser` / `get_optional_user` / `require_admin` JWT 依赖。

### 4.3 路由接入现状 ✅

| 路由组 | 接入方式 |
|---|---|
| `/problems` 列表 | 可见集 SQL：公有 ∪ 我的 ∪ 我的团队的（三段 OR，含归档过滤） |
| `/problems/{id}` 详情/编辑/数据 | `ProblemAccess("view")` / `("manage")` |
| `/contests` 全套 | `ContestAccess`；报名/参赛者另有 `contest_participants` 校验 |
| `/playlists` 全套 | `PlaylistAccess` |
| `/teams` 全套 | `can_view` + `require_team_manage` |
| `/submissions` | 题目可见性 + 赛中报名；结果明细另有防打表控制 |
| `/admin/*` | 整组 `require_admin`（不依赖资源规则，ADMIN 全量） |
| `/assistant/*` | 见 §6 |

### 4.4 数据库落地 ✅

一个迁移族内完成：`teams` / `team_members` / `playlists` / `playlist_problems` 四张新表，`problems` / `contests`（及 `playlists` 建表即带）`owner_type` 列；存量数据 owner_type 默认 `user` 自洽，`owner_id` 未动。

## 5. 题单（Playlists）

按设计建表落地，**一处删减**：

- `playlists`（title/description/is_public/owner_type/owner_id）+ `playlist_problems`（含 `idx` 顺序、UNIQUE(playlist,problem)）✅
- **`playlist_progress` 表未建**——进度实时算：`GET /playlists/{id}` 详情返回 `solved_problem_ids`（该用户在这些题上 AC 过的题号集合，现算自 submissions），前端据此画打卡状态。避免一张可与 submissions 推导的冗余表。
- 题单删除为**真删**（级联清 `playlist_problems`，题目本体不受影响）；题单内题目对成员按 §2.2 间接可见。
- 团队题单、私有题单内题目提交均已放行（成员对团队资源可见即可交）。

## 6. AI 助手对权限体系的复用

助手工具面不另造一套权限，全部复用本文判定（详见 docs/AI助手Agent设计.md §5/§7）：

- `_resolve_context` 的 `problem_review` 分支：载题 + **实时 `can_manage`** 校验，不通过静默降级为空上下文（不给探测信号，与 404 防探测同一思路）；
- 审校工具 handler 首行 `_require_review(ctx)` 纵深防御：`ctx["review"]` + 再查 `can_manage`；
- 工具函数第一个参数恒为 `current_user`（后端循环注入，模型无法伪造），`search_problems`/`get_problem` 等走与题列表相同的可见性 SQL；
- 声明面即权限边界：学生会话的 tools_json 里根本没有审校工具声明。

## 8. 设计稿 → 实际的差异汇总

| 设计稿 | 实际落地 | 原因 |
|---|---|---|
| 四级全局角色 | 两级 USER/ADMIN | 中间角色与资源级权限重复，废弃 |
| 间接可见性反查宿主 | `?contest_id=` / `?playlist_id=` 载体参数 | 反查全部宿主代价高且语义含糊；载体是用户意图的自然表达 |
| `playlist_progress` 表 | 不建，详情接口实时算 `solved_problem_ids` | 冗余可从 submissions 推导 |
| 邀请码落库 | 进程内存（重启失效），**待办** | 一期从简，见项目计划 §4 |
| 公开申请制/可见性白名单/分组报名/容量配额 | 未做（团队已有容量与归档） | 留在后续规划 |
