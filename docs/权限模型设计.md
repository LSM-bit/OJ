# 权限模型设计：公有/私有资源 + 团队 + 路由权限认证

> 编写日期：2026-09-07
> 状态：**设计稿（待实现）**
> 关联：docs/项目计划.md 第 3.1 / 3.2 / 3.4 / 3.5 节

---

## 1. 设计目标

1. **题目 / 比赛 / 题单**三类核心资源都区分**公有（public）与私有（private）**
2. 用户可以组成**团队**（发起人=队长），资源归属可以是「个人 / 团队 / 平台」
3. 所有权限校验**收敛到路由层**（FastAPI Depends），业务路由只声明需要什么权限，不写散落的 if 判断
4. 一条统一的**资源可见性判定规则**，题目/比赛/题单共用

---

## 2. 可见性判定规则（核心）

资源 R（题目/比赛/题单）对用户 U 可见，当且仅当满足其一：

```
1. R.is_public = true                          （公有资源，所有人可见）
2. R.owner_type = 'user'  且 R.owner_id = U.id  （个人私有资源）
3. R.owner_type = 'team'  且 U 是该团队成员      （团队资源，任何成员可见）
4. R 在某场比赛/题单内，且 U 对该比赛/题单可见    （间接授权，见 2.2）
5. U.role = ADMIN                               （管理员全量可见）
```

### 2.1 三类资源归一化

题目、比赛、题单都用同一套字段表达归属与可见性：

| 字段 | 类型 | 说明 |
|---|---|---|
| `owner_type` | Enum(`user` / `team`) | 归属个人或团队 |
| `owner_id` | BigInteger | user.id 或 team.id |
| `is_public` | Boolean | 公有/私有 |

> 现有表已有 `owner_id` + `is_public`，新增 `owner_type`（默认 `user`）即可平滑迁移。
> `owner_id` 含义从"用户 id"扩展为"user_id 或 team_id"，由 owner_type 消歧。

### 2.2 私有题目通过比赛/题单间接可见

- 私有题目挂在**公有比赛**里 → 比赛期间对该比赛可见（现有行为保留）
- 私有题目挂在**私有比赛/私有题单**里 → 只有能看见比赛/题单的人看见题目
- 实现：题目详情接口查 `contest_problems` / `playlist_problems` 反查宿主资源，任一宿主可见即可见

### 2.3 操作权限（写操作）与可见权限（读操作）分离

| 操作 | 允许的人 |
|---|---|
| 读（查看题面/榜单/题单内容） | 满足第 2 节可见性 |
| 写（编辑题目/比赛/题单配置） | `owner_type=user`：owner 本人；`owner_type=team`：队长 + 副队长（见 §4.2）；ADMIN |
| 管理数据（上传测试数据等） | 同写权限 |
| 提交（对题目/比赛内题目提交） | 可见 + 比赛场景需已报名 |

## 3. 团队模型

### 3.1 表结构（新增 2 张表）

```sql
teams(
    id            BIGINT PK,
    name          VARCHAR(64) UNIQUE,      -- 团队名
    description   TEXT DEFAULT '',
    owner_id      BIGINT FK users.id,      -- 发起人 = 队长
    max_members   INT DEFAULT 50,          -- 人数上限
    created_at    TIMESTAMPTZ
)

team_members(
    id         BIGINT PK,
    team_id    BIGINT FK teams.id ON DELETE CASCADE,
    user_id    BIGINT FK users.id,
    role       team_member_role,           -- owner / admin / member
    joined_at  TIMESTAMPTZ,
    UNIQUE(team_id, user_id)
)
```

### 3.2 团队角色

| 角色 | 权限 |
|---|---|
| `owner`（队长） | 团队全部管理权：解散、转让队长、增删管理员、审核加入申请、管理团队资源（建/改/删团队题目、比赛、题单） |
| `admin`（副队长/管理） | 队长授权：管理团队资源、审核加入申请（二期可裁剪） |
| `member`（队员） | 查看团队私有资源（题单/题目/比赛）、参加团队赛 |

- 发起人创建团队时自动成为 `owner`
- 队长转让：`owner` → 指定成员置为 `owner`，原队长降为 `admin`
- 加入方式：一期实现**邀请制**（队长/副队生成邀请码，用户凭码加入）；公开申请制放二期

### 3.3 团队与 RBAC 的关系

- 团队角色（owner/admin/member）是**资源维度**的权限，与用户全局角色（USER/PROBLEM_SETTER/...）**正交**
- 判定写权限时：全局 ADMIN 放行；否则查资源 owner_type：
  - `user` → owner_id == 当前用户
  - `team` → 当前用户是该团队 owner/admin 角色

## 4. 后端实现方案

### 4.1 统一权限服务层

新增 `api/app/services/access.py`，所有判定函数集中在这里，路由层只调用不实现：

```python
async def can_view(db, user, owner_type, owner_id, is_public) -> bool:
    """资源可见性：§2 的 5 条规则"""

async def can_manage(db, user, owner_type, owner_id) -> bool:
    """写权限：个人=本人；团队=owner/admin 团队角色；ADMIN"""

async def get_team_role(db, team_id, user_id) -> TeamRole | None:
    """查询用户在某团队的角色"""
```

### 4.2 路由依赖（FastAPI Depends 工厂）

权限以**依赖工厂**形式挂在路由上，拒绝时统一 403/404：

```python
# 路径携带资源 id 的场景，用工厂生成依赖
def ProblemAccess(action: Literal["view", "manage"]):
    """GET /problems/{id} 用 view；POST/PUT/DELETE 用 manage"""
    async def checker(problem_id: int, db=Depends(get_db), user=CurrentUser):
        p = await db.get(Problem, problem_id)
        if p is None:
            raise HTTPException(404, "题目不存在")
        ok = await (can_view if action == "view" else can_manage)(db, user, p.owner_type, p.owner_id, p.is_public)
        if not ok:
            raise HTTPException(404, "题目不存在")   # 私有资源统一 404，防探测
        return p
    return checker

# 使用：
@router.get("/{problem_id}")
async def get_problem(p: Problem = Depends(ProblemAccess("view"))): ...
```

- **私有资源 403 vs 404**：对不可见的私有资源一律返回 404（与"不存在"同响应），防止枚举探测；管理类操作（有查看权但无写权）才返回 403
- 比赛路由做 `contest_id` 参数名适配（ContestAccess）；题单路由同理（PlaylistAccess）

### 4.3 现有路由改造点

| 路由 | 现状 | 改造 |
|---|---|---|
| `GET /problems` | 只列 is_public | 公有 + 我拥有的 + 我团队拥有的（SQL 三段 OR） |
| `GET /problems/{id}` | 只查 is_public | 换 ProblemAccess("view") |
| `POST /problems` | owner_id=user.id | 增加可选 `owner_type=team, team_id=X`（校验团队管理权） |
| `POST /problems/{id}/data` | 手写 owner 判断 | 换 ProblemAccess("manage") |
| `GET /contests` | 列全部 | 同题目列表：公有 + 自己的 + 团队的 |
| `GET /contests/{id}`、`standings`、`register` | 无权限判断 | 换 ContestAccess("view") |
| `POST /contests` | ContestAdminDep（全局角色） | 保留全局角色门槛（能办赛的人），归属可选个人/团队 |
| 提交路由 | 手写 participant 判断 | 可见性 + 报名校验保留 |

### 4.4 数据库迁移（Alembic，一个 migration）

1. 新建 `teams`、`team_members` 表
2. `problems` / `contests` / 新表 `playlists` 增加 `owner_type` 列（`Enum('user','team')`，默认 `'user'`，非空）
3. 现有 `owner_id` 不动（历史数据全是用户 id，与默认 owner_type='user' 自洽）
4. 新增 `playlists` 表（题单，一并购入，见 §5）

## 5. 题单（Playlists）——一并纳入权限体系

题单是第三个直接需要公有/私有的资源，趁权限模型落地一并建表：

```sql
playlists(
    id          BIGINT PK,
    title       VARCHAR(128),
    description TEXT DEFAULT '',
    is_public   BOOLEAN DEFAULT false,
    owner_type  Enum('user','team') DEFAULT 'user',
    owner_id    BIGINT,                       -- user.id 或 team.id
    created_at  TIMESTAMPTZ
)

playlist_problems(
    id          BIGINT PK,
    playlist_id BIGINT FK playlists.id ON DELETE CASCADE,
    problem_id  BIGINT FK problems.id,
    idx         INT,                          -- 顺序
    UNIQUE(playlist_id, problem_id)
)

-- 进度追踪（刷题打卡用）
playlist_progress(
    id          BIGINT PK,
    playlist_id BIGINT,
    user_id     BIGINT,
    problem_id  BIGINT,
    solved_at   TIMESTAMPTZ,
    UNIQUE(playlist_id, user_id, problem_id)
)
```

> 进度只记首次 AC 的时间；题单内题目必须是**对该用户可见**的题目（加入时校验管理权，查看时校验题目可见性）。

## 6. API 设计汇总（新增/改造）

### 团队
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/teams` | 创建团队（发起人=队长） |
| GET | `/teams` | 我的团队列表 / 公开搜索 |
| GET | `/teams/{id}` | 团队详情（成员名单，非成员只看基本信息） |
| PUT | `/teams/{id}` | 编辑（队长/副队） |
| DELETE | `/teams/{id}` | 解散（队长） |
| POST | `/teams/{id}/members` | 凭邀请码加入 |
| DELETE | `/teams/{id}/members/{user_id}` | 移除成员（队长）/ 退出（本人） |
| PUT | `/teams/{id}/members/{user_id}/role` | 设置副队长 / 转让队长（队长） |
| POST | `/teams/{id}/invite-codes` | 生成邀请码（队长/副队） |

### 题单
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/playlists` | 创建（个人/团队） |
| GET | `/playlists` | 可见列表（公有+我的+团队的） |
| GET | `/playlists/{id}` | 详情含题目列表（PlaylistAccess view） |
| PUT | `/playlists/{id}` | 编辑（manage） |
| PUT | `/playlists/{id}/problems` | 增删题目、调整顺序（manage） |
| GET | `/playlists/{id}/progress` | 我的进度 |

### 归属扩展
- `POST /problems`、`POST /contests` body 增加：
  ```json
  {"owner_type": "team", "team_id": 5}
  ```
  缺省 = 归属个人
