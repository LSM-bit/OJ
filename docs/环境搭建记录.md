## 已验证的端到端链路

```
提交代码 (python3.12 A+B)
  → FastAPI /dev/smoke-judge
  → gRPC 网关 (api:50051) 下发 SubmitJob
  → judge-node 容器 (nsjail 沙箱) 编译/运行/比对
  → JudgeResult 回传 → {"status": "accepted", "score": 20}
```

## 本地启动步骤

```bash
# 1. 基础设施（postgres + redis + judge-node）
cd deploy && docker compose up -d --build

# 2. API（含 gRPC 网关 :50051）
cd api
.venv/Scripts/python -m uvicorn app.main:app --port 8000

# 3. 前端（可选）
cd web && npm run dev   # :5173

# 4. 冒烟测试（需 judge-node 已注册）
curl -X POST http://localhost:8000/dev/smoke-judge
# 期望: {"status":"accepted","score":20,...}
```

## 架构要点（实现中确定的）

1. **判题协议**：`api/protos/judge/v1/judge.proto`（自有协议）
   - `Connect` bidi 流：Register → Ack → SubmitJob → JudgeResult，心跳 10s
   - `FetchProblemData` 服务端流：题目测试数据分块下发（manifest.json + cases/*.in/.out）
   - 节点缓存键：`{problem_id}-{data_version}`，数据版本更新自动失效
   - 状态字符串：`accepted / wrong_answer / time_limit_exceeded / memory_limit_exceeded /
     output_limit_exceeded / runtime_error / compile_error / system_error`
   - proto 生成代码两处使用：`api/app/judge_gateway/gen/`（服务端）、
     `judge/judge_node/gen/`（客户端），生成命令：
     `python -m grpc_tools.protoc -I protos --python_out=... --grpc_python_out=... protos/judge/v1/judge.proto`
     （注意两处生成代码的 import 路径不同，judge 侧用 `from gen.judge.v1 import`）

1b. **AI 助手协议**：`agent/protos/assistant/v1/assistant.proto`（与判题协议分文件，消息演进节奏不同）
   - `Connect` bidi 流：Register → Ack；下行 ChatJob/ToolResult/CancelChat，上行 Heartbeat/ChatDelta/ChatDone/ChatError
   - 会话消息与工具结果整体走 JSON 字符串字段（Anthropic blocks 原样），proto 保持薄
   - 生成代码两处使用：`api/app/assistant_gateway/gen/`、`agent/assistant_node/gen/`，生成命令（在 `agent/` 目录下）：
     `python -m grpc_tools.protoc -I protos --python_out=assistant_node/gen --grpc_python_out=assistant_node/gen protos/assistant/v1/assistant.proto`
     （API 侧同理 `-I ../agent/protos --python_out=app/assistant_gateway/gen ...`；两侧生成后均需 sed 修 import 为包内相对路径）

2. **沙箱**：nsjail（源码编译，镜像内 /usr/local/bin/nsjail），配置 `deploy/nsjail.cfg`
   - 根目录只读 + `/tmp`、作业目录 `--bindmount`（rw）挂入
   - 网络/用户/PID/IPC/UTS namespace 全隔离，非 root（nobody）运行
   - 资源限制运行时覆盖：`--rlimit_as`（内存）、`--rlimit_fsize`（输出）、`--rlimit_nproc`
   - 坑：nsjail 不继承宿主挂载，作业目录必须显式 `--bindmount <cwd>`，否则读不到源文件（表现为 RE）

3. **判题节点镜像**：`deploy/judge-node.Dockerfile`
   - ubuntu:24.04 + python3.12/g++/gcc/openjdk-21 + nsjail（源码编译，kafel 子模块手动克隆）
   - apt 用阿里云 http 源（https 证书链不可用）、pip 用清华源

4. **网关调度**：`api/app/judge_gateway/gateway.py`
   - 节点容量信号量（capacity），无空闲节点时任务排队
   - gRPC bidi 流的服务端实现：一个 generator 输出下行消息 + 一个 reader task 消费上行

5. **Windows 开发环境**：判题必须在 Linux 容器内（nsjail）；API 跑在宿主机
   - judge-node 容器访问宿主机 API 用 `host.docker.internal:50051`
   - 容器网络抽风时 `docker compose rm -sf judge-node && up -d` 重建即可
