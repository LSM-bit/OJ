## 当前本地启动步骤

Windows 一键：双击根目录 `run.bat`（`run.bat stop` 停容器）。手动：

```bash
# 1. 基础设施 + 两个计算节点
#    （postgres + redis + minio + go-judge 沙箱 + judge-node + assistant-node）
cd deploy && docker compose up -d --build

# 2. 后端 API（同一进程监听 HTTP :8000、判题网关 :50051、助手网关 :50060）
cd api
python -m venv .venv && .venv/Scripts/pip install -e .
.venv/Scripts/alembic upgrade head     # ★ 迁移务必与重启同批，见「教训」
.venv/Scripts/uvicorn app.main:app --reload --port 8000

# 3. 前端
cd web && npm install && npm run dev   # :5173
```

健康检查：API `:8000/health`（内嵌判题/助手节点注册状态）、沙箱 `:5050/version`、MinIO Console `:9001`。

冒烟验证不再走专用端点（`/dev/smoke-judge` 已随鉴权接入删除）——直接在前端注册登录、上传题、提交判题即可走通全链路；`pytest`（128 用例，SQLite + mock 双节点）本身就是可重放的端到端。

助手节点可以不进容器、宿主机直起：`cd agent && pip install -e . && python -m assistant_node.daemon`；没配 `ANTHROPIC_API_KEY` 时设 `ASSISTANT_MOCK=1` 走 mock 回显（compose 里该服务留有注释开关）。

## 判题链路（阶段 0 确定，至今未变）

1. **判题协议**：`api/protos/judge/v1/judge.proto`（自有协议）
   - `Connect` bidi 流：Register → Ack → SubmitJob → JudgeResult，心跳 10s
   - `FetchProblemData` 服务端流：题目测试数据分块下发（manifest.json + cases/*.in/.out）
   - 节点缓存键：`{problem_id}-{data_version}`，数据版本更新自动失效
   - 状态字符串：`accepted / wrong_answer / time_limit_exceeded / memory_limit_exceeded /`
     `output_limit_exceeded / runtime_error / compile_error / system_error`
   - proto 生成代码两处使用：`api/app/judge_gateway/gen/`（服务端）、`judge/judge_node/gen/`（客户端），生成命令：
     `python -m grpc_tools.protoc -I protos --python_out=... --grpc_python_out=... protos/judge/v1/judge.proto`
     （注意两侧 import 路径不同，judge 侧用 `from gen.judge.v1 import`）

2. **沙箱**：nsjail（源码编译进镜像 `/usr/local/bin/nsjail`；最终选型放弃 go-judge HTTP 接口方案），配置 `deploy/nsjail.cfg`
   - 根目录只读 + `/tmp`、作业目录 `--bindmount`（rw）挂入
   - 网络/用户/PID/IPC/UTS namespace 全隔离，非 root（nobody）运行
   - 资源限制运行时覆盖：`--rlimit_as`（内存）、`--rlimit_fsize`（输出）、`--rlimit_nproc`
   - 坑：nsjail 不继承宿主挂载，作业目录必须显式 `--bindmount <cwd>`，否则读不到源文件（表现为 RE）
   - 实测 12 场景（AC/WA/TLE/MLE/RE/CE/OLE/SE/爆内存/fork 限制/中文输出/大文件）状态分类全对
   - 内存计量：进程树 VmHWM 周期采样取最大（`judge/judge_node/executor.py`），维持此粗估方案——cgroup 精确计量在 nsjail 非 cgroup namespace 模式下收益不明显，未再投入

3. **判题节点镜像**：`deploy/judge-node.Dockerfile`
   - ubuntu:24.04 + python3.12/g++/gcc/openjdk-21 + nsjail（源码编译，kafel 子模块手动克隆）
   - apt 用阿里云 http 源（https 证书链不可用）、pip 用清华源

4. **网关调度**：`api/app/judge_gateway/gateway.py`
   - 节点容量信号量（capacity），无空闲节点时任务排队
   - gRPC bidi 服务端：一个 generator 输出下行消息 + 一个 reader task 消费上行
   - `RunCode` 通道（自测/助手 `run_on_sample` 共用）：只跑公开样例、紧限额（2s/64MB），不产正式提交记录

5. **Windows 开发环境**：判题必须在 Linux 容器内（nsjail）；API 跑宿主机
   - 容器访问宿主机网关用 `host.docker.internal:50051`（助手 `:50060` 同）
   - 容器网络抽风时 `docker compose rm -sf judge-node && up -d` 重建即可

## 助手链路（阶段 7 加入）

1b. **AI 助手协议**：`agent/protos/assistant/v1/assistant.proto`（与判题协议分文件，消息演进节奏不同）
   - `Connect` bidi 流：Register → Ack；下行 ChatJob/ToolResult/CancelChat，上行 Heartbeat/ChatDelta/ChatDone/ChatError
   - 会话消息与工具结果整体走 JSON 字符串字段（Anthropic blocks 原样），proto 保持薄
   - 生成代码两处使用：`api/app/assistant_gateway/gen/`、`agent/assistant_node/gen/`，生成命令（在 `agent/` 目录下）：
     `python -m grpc_tools.protoc -I protos --python_out=assistant_node/gen --grpc_python_out=assistant_node/gen protos/assistant/v1/assistant.proto`
     （API 侧同理 `-I ../agent/protos --python_out=app/assistant_gateway/gen ...`；两侧生成后均需把 import 修成包内相对路径）

6. **助手节点镜像与端口**：`deploy/assistant-node.Dockerfile` + compose `assistant-node` 服务
   - **非 privileged**（无沙箱，纯模型 I/O），`restart: unless-stopped`
   - 网关端口 **50060**——原定 50052 与本机 IncrediBuild LicenseService 冲突，改端口并写进 `config.py assistant_grpc_port`
   - `ANTHROPIC_API_KEY` 等密钥经 `env_file: ../.env` 注入而非 compose 内联 `${VAR}`——**内联会被宿主 shell 提前插值**（PowerShell 下取空值），实测教训
   - key 只存节点侧 env；API 进程与 git 均不持有

## 教训（踩过一次，记下来别再踩）

- **alembic 迁移与 API 重启必须同批**：`--reload` 只重载代码不会跑迁移，新表/新列查询直接 500。改完 models 的提交里带上迁移文件，起服务前先 `alembic upgrade head`。
- **Vue 响应性**：往数组 push 后必须取数组尾代理再增量改写，拿裸对象直写不触发更新（曾导致 AI 流式输出全程不可见、结束时整段刷出）。详见 docs/AI助手Agent设计.md §9。
- nsjail `--bindmount` 坑见上文第 2 条；`--rlimit_as` 对 Java 需另配 `-Xmx` 兜底。
- 本地若同时跑多个 alembic head（分叉迁移）会在 `upgrade head` 直接报错——合分支后记得 `alembic heads` 确认单 head（当前：`dd44ee55ff66`）。
